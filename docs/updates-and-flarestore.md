# FlareStore source and upstream updates

Add this source URL in FlareStore (or a compatible AltStore-format client):

https://github.com/9pbpsvr6f9-alt/aiostreams-ios/releases/latest/download/source.json

It includes separate iPhone/iPad and Apple TV apps. Your sideloader must support
the selected platform. IPAs are unsigned; the sideloader signs them at install time.
Refresh the source to see new versions, then choose the update in your sideloader.
This does not provide silent iOS updates or bypass signing/refresh requirements.

The source is generated by `scripts/update-source.py` from both built IPAs. It
uses their actual bundle IDs, minimum OS, version, privacy declarations and byte
sizes. `developerName` is the alt username. The source and icon are uploaded with
the IPAs to one draft release, which is made public only after all uploads pass.
Old versions retain permanent, versioned asset URLs. No expiring Actions download
URLs are put in the feed. The generated `altstore/source.json` is a release asset,
not a manually maintained list of guessed build metadata.

## Workflow

Once these workflows are on the default branch, `Check upstream updates` runs
daily and can also run manually. Enable GitHub Actions and the repository Actions
setting “Allow GitHub Actions to create and approve pull requests” so it can open
PRs (it does not approve or merge them). It follows official web main and the
reference tvOS app main. The official commit is pinned in `web/AIOSTREAMS_REF`;
`web/TVOS_REFERENCE_REF` records the last reference revision checked. A reference
change creates a comparison to review, not an automatic native-code port.

One `automation/upstream` PR is updated, and a candidate Mac build is explicitly
dispatched because PRs created by GITHUB_TOKEN don't start PR workflows themselves.
A drifting host patch stops the build and needs manual repair. A passing build
does not prove all upstream native features have been ported.

After review and a merge into main, a successful main build publishes a new
`0.2.<workflow run number>` release and refreshes the source. Failed builds and PR
builds never publish. For an initial release from a feature branch, dispatch
`Build IPA` on that branch with `publish_release` enabled. Web-ref overrides and
optional height-channel builds cannot publish. The run number supplies unique
marketing/build versions in both apps, so feed clients can detect upgrades.

No merge is performed as part of preparing this setup. GitHub scheduled workflows
only run from the default branch, so daily checking remains inactive until this PR
is merged. The manually published initial release/source works before that merge.

## Privacy and validation

`AGENTS.md` records the approved alt Git identity. Local pre-commit/pre-push hooks
reject other author or committer identities; enable them with
`git config --local core.hooksPath .githooks`. Bot-created commits explicitly use
GitHub Actions' no-reply identity. Existing historical commits are not rewritten.

Run `python3 -m unittest discover -s tests -v`, `bash -n scripts/*.sh`, and the
privacy checks before publishing. Native builds run in the Mac workflow. On an
iPhone, verify Settings → Subtitles offers Smaller below Small, that your existing
subtitle styling is retained, and that the feed's version matches the installed app.

If hosted macOS ARM capacity prevents a candidate from starting, manually dispatch
Build IPA with `runner: macos-15-intel`. This fallback validates candidates only;
it cannot publish a release. Release builds retain the standard macos-26 runner.
